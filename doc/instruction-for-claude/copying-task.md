## タスク
基本的に https://arxiv.org/abs/2102.02611 の"Copy Memory Problem"を踏襲する
* 語彙は0~9のdigit（語彙数10）
* 入力長はTをパラメータとしてT+20
  - 最初の10文字は1~8のランダム
  - 次のT-1文字は0で埋める
  - 末尾11文字は9で埋める
  - ターゲットは先頭T+10文字を0埋め、末尾10文字を入力の先頭10文字とする

# 計画 (Claude追記)

## 関連論文の確認結果
* **CKConv (arXiv:2102.02611)** のCopy Memory Problem定式は本ドキュメントの仕様と一致することを確認:
  先頭10文字が{1..8}ランダム、次のT-1文字が0、**末尾11文字が9**(delimiter)、総長T+20。
  ターゲットは末尾10位置で先頭10文字を再現、**それ以外の位置では0を出力**(=全位置で損失を取る)。
* **Mamba (arXiv:2312.00752)** Fig.2: 標準Copyingは入出力の間隔が一定なため「時間認識(time-awareness)だけで解ける」
  (LTIモデルでも可能)。content-aware性が要るのはSelective Copying。まずCopyingでベースライン能力を確認し、
  次段階でSelective Copyingに進むのが自然な順序。合成タスクは2層・d_model 64〜128の小モデルで行われている。
* **Repeat After Me (arXiv:2402.01032)**: コピーの長さ汎化は位置埋め込みに強く依存
  (絶対位置埋め込みは訓練長で急落、NoPE/ALiBi系は外挿しやすい)。評価はtoken accuracyと
  string accuracy(10文字完全一致)の両方を見るのが標準。
  RecursiveCompressorは絶対位置埋め込みを持たない(チャンク内周期pos_emb + 階層構造の暗黙位置のみ)ため、
  **長さ外挿に構造的に有利という仮説が立つ — 本検証の見どころ**。

## 設計判断
### タスク/損失
* 入出力は**同位置対応のseq2seq形式**(RNN文献の標準)。`RecursiveCompressorLM.forward(input_ids, labels)`は
  同位置でlogitsとlabelsを比較する実装なので、シフトなしでそのまま使える(causalなので位置tは入力0..tを参照可能)。
* 損失は**全位置CE**(0埋め位置も「0を出力」として学習)をデフォルトとする。CKConv等の既存研究と整合。
  比較用に末尾10位置のみ(-100マスク)も`--loss-positions answer`オプションで残す。
* PADトークンは追加しない: **バッチ内でTを固定**(バッチごとにTをサンプル)すれば全サンプル同長でパディング不要。
  語彙数はちょうど10のまま。

### モデル (デフォルト)
* d_model=512, num_heads=8, d_ff=1024, num_layers=2, chunk_size=4, compress_size=1 (~11Mパラメータ)
* compress_size=1が最も厳しい情報ボトルネック(10桁≈33bitを1ベクトルの再帰圧縮で運ぶ)。
  失敗時はcompress_size=2,4のablationで容量起因かを切り分ける。

### 学習
* **オンライン生成**(毎バッチ新規サンプル、エポック概念なし)。データセットサイズの問いは消滅、
  ステップ数で管理。再現性はseed固定で担保。
* 訓練T ~ U[1, 2028] (最大コンテキスト2048-20)。バッチ内T固定、バッチごとに再サンプル。
* バッチサイズ64、50kステップを初期値に(短いTのバッチは軽いので平均的には速い)。
* 単GPU・AdamW(lr 3e-4, warmup 1k, その後cosineなし固定)をデフォルトに。
  本番のMuon+ReduceLROnPlateauは持ち込まない(検証の変数を減らす。既存研究もAdam系)。
* bf16 autocast (本番と同じ数値環境)。

### 検証
* T grid: {1..14の全点} ∪ {16, 24, 32, 48, 64, ..., 131072}(2^kと中間点)。各Tで256サンプル。
* メトリクス: **token accuracy**(末尾10位置)と**string accuracy**(10文字完全一致)の両方をJSON保存。
* プロット: 横軸log T、縦軸accuracy、訓練ホライズン(T=2028)に縦線。token/string両曲線。PNG保存。
* 評価はforward一括(hiddenの逐次生成は不要、教師強制でlogits argmaxを取るだけ)。
  チャンクattentionなのでT=131072でもO(L)メモリ、batch縮小で対応。

### 事前に必要なコード修正
* **不要と判明(訂正)**。`_num_queries()`の`log(65536)`ハードコードは当初「系列長65536超で
  クエリスロット不足」と考えたが、検証の結果**現アーキテクチャでは機能的に無害**:
  - スロットは全てNoneプレースホルダで、再帰中に尽きてもcomp_query=None→チャンク末尾
    ベクトルからの導出で継続する(レイヤ0の全レベルと同じ経路)。出力リストは実深度まで
    伸長するのでレイヤ間クエリ伝播も全深度で保たれる
  - 実測: スロット数9→2に減らしてもlogits完全一致(diff=0)、T=131072(系列長131092)の

  - 旧アーキテクチャ(学習可能クエリを上から配る方式)の遺物であり、いずれ削除してよい
* 評価時のメモリが厳しい場合は`step()`によるチャンク分割推論(hidden引き継ぎ)が使える
  (フルforwardとの差は丸め誤差レベルであることをT=131072で実測確認済み)。
  hiddenはO(log L)と極小なので長いTでも評価バッチを大きくできる。

## スモークテスト結果 (2026-08-16, 重要な発見)
小型モデル(d=128, 2層)によるスモークで、**現アーキテクチャはT=1(系列長21)ですらコピーを
解けない**ことが判明。実装のバグではなく構造的な挙動と考えられる:

* T~U[1,16]・全位置loss・6000step: token acc 0.116 = チャンス(1/8)に完全に張り付き
  (「answer位置で一様分布を出す」局所解。lossはその理論値0.73と一致)
* T=1固定・answer-only loss: 学習は立ち上がる(0.11→0.52)が**0.52で飽和**。
  15000stepまで回しても0.5196で微動せず(grokking的な遅延立ち上がりではない)
* compress_size=1→8で結果が**全く変わらない**(0.516) → 記憶容量の問題ではない
* 桁別の内訳: **memory[0]とmemory[9]は100%、中間桁は0.29-0.50** —
  階層圧縮が「桁の順序・位置の同一性」を保持できないbag-of-tokens的挙動
* 感度分析(ランダム初期化): 先頭10桁→末尾10位置のlogit感度はT=1で0.43、
  **再帰1階層ごとに約1/10に指数減衰**(T=64で0.001)。因果的には届くが信号が薄い

### 示唆される構造的原因(仮説)
1. **階層をまたぐ位置情報の欠如**: pos_embはチャンク内4周期のみ。マーカー領域のチャンク
   (9,9,9,9)は内容が同一で、「自分が何番目の出力チャンクか」をouter context経由でしか
   知り得ない。圧縮列に位置情報を付与する機構がない
2. **attention圧縮の置換不変性**: クエリ1個のattention圧縮は加重平均であり、
   チャンク内pos_emb以外に順序を保つ帰納バイアスがない。先頭/末尾だけ取れて中間が
   混ざるのは典型的な症状
3. 信号の指数減衰(gated attentionのsigmoid≈0.5が階層ごとに掛かる等)

### 次の一手の候補
* 圧縮列(レベル1以上)への位置情報付与(レベル別pos_emb、または圧縮時に系列位置を注入)
  - ※レベル別pos_embは「メモリの許す限り無限に生成する」という設計目標と相性が悪いので避けたい。
    レベル**共通**の相対位置バイアス(ALiBi的、圧縮attention/decompressorに適用)なら長さ非依存で両立可能
* decompressorのkvを「直前チャンクの圧縮1点」から「過去数点」に広げる(局所検索の強化)
* ~~gateの初期バイアスを開く(sigmoid≈1で初期化)ことで信号減衰を緩和~~ → **検証済み、微改善のみ(下記)**
* まず自然言語で性能が出ている理由との整合を考える(局所n-gram + 大意の圧縮で
  十分なタスクでは順序保持の弱さが顕在化しない)

### ALiBi化の検証結果 (2026-08-16)
`compressor_query_pos`を削除し、ALiBi相当のヘッド毎スロープ(2^(-8h/H)、固定・非学習)を
attention logitに加算する方式に変更:
* encoder(チャンク内causal self-attn): 標準ALiBi `-m_h*(i-j)`、causalマスクは-infで焼き込み
* compressor(圧縮クエリ→チャンク内4点): kv位置のチャンク末尾からの距離 `-m_h*(C-1-j)`
* decompressor: kvに位置構造がないため適用外
* バイアスはチャンク内相対距離のみの固定バッファで全レベル共有 → **長さ非依存、無限生成と両立**
* 注意: バッファはpersistent必須(persistent=Falseだとfrom_pretrainedのmeta-device初期化で
  未初期化になる HFの落とし穴を踏んだ)

結果:
* ランダム初期化の感度: ゲート開放比でさらに2倍前後改善(T=16: 0.024→0.053, T=256: 0.0001→0.00035)
* **T=1学習: 0.528で飽和 — 壁は破れず**(ベースライン0.516/ゲート開放0.530と同水準)
* 消去法更新: 容量✗、ゲート減衰✗、attention logitへの位置バイアス✗
* 次の仮説: 記憶10桁がチャンク境界(4)と非整合(10=2.5チャンク)で、出力位置も
  チャンク途中(11)から始まるため、「チャンク粒度のouter要約」と「桁単位でスライドする
  入出力対応」が噛み合っていない可能性。出力チャンクごとに必要な4桁の窓がずれる
  (c3→m1-m4, c4→m5-m8)が、outerはチャンク単位でしか変化しない。
  → decompressorのkv拡張(過去k点の圧縮を見せて桁単位の検索を可能にする)が次の本命

### kv拡張(retrieve_size)の検証結果 (2026-08-16)
decompressorのkvを「直前チャンクの圧縮1点」→「過去retrieve_size(=k)チャンクの圧縮列」に拡張:
* `retrieve_size`をconfigパラメータ化(デフォルト4)、`initial_context`を(k, S, d)に拡張(学習可能)
* 窓は`cat([prev_outer, compressed_out])`からのunfoldスライシングで実装。先頭チャンクは
  initial_contextとの混合窓になり特別分岐なし。hiddenのouterは直近k点(B, k, S, d)
* decompressorにチャンク距離のALiBiバイアス`-m_h*(k-1-w)`を追加
* step/forward等価性は窓境界をまたいでも維持(全74テストパス)

結果: **T=1で0.5295 — 壁は不変**。cs=4+k=4の組でも0.53。

### 重要な発見: compress_sizeクエリの縮退
compress_size(S)>1のクエリはS本とも「チャンク末尾ベクトル由来の同一値」で、compressorの
ALiBiバイアスもS軸にexpandした同一値のため、**S本のクエリが完全に縮退して実質1本**になっている
(残差もattention入力も同一 → 出力も同一)。compress_size=8で結果が変わらなかった過去の実験も
これで説明がつく。**S>1は現状机上のパラメータで、圧縮容量は常にd_model 1本分**しかない。

修正案(次の一手): compressorのALiBiバイアスをクエリ別にして対称性を破る —
`bias[h,s,j] = -m_h * |c(s) - j|`、`c(s) = s*(C-1)/(S-1)` (クエリsがチャンク内位置c(s)近傍を
担当)。S=C=chunk_sizeなら各クエリが1トークンずつ担当し、圧縮が順序保存の再配列に近づく。
decompressorはk*S点の窓から素直なattention検索で任意の桁を取り出せるようになる。
学習可能パラメータ追加なし・長さ非依存でALiBiの設計思想とも整合。

### クエリ縮退解消の検証結果と真のボトルネック特定 (2026-08-16)
compressorのALiBiバイアスをクエリ別に一般化(クエリsが担当位置c(s)=s(C-1)/(S-1)近傍を選好、
`-m_h*|c(s)-j|`。S=1は従来の末尾距離とビット一致)。S=4でクエリの縮退は解消したが、
**T=1は0.5295で壁は不変**。

per-digit分析で決定的なパターンを確認:
* m0(チャンクc2担当)とm9(c5担当): **100%** — そのチャンクが出すべき答えが1桁だけのケース
* c3担当のm1-m4、c4担当のm5-m8: 0.37-0.44で均等に低い — 1チャンクが4桁を出すケース
* 検算: (2×1.0 + 8×0.41)/10 = 0.528 ≈ 観測値0.5295。全構成が同値に収束した理由も説明可能

**真のボトルネック: decompressor(cross-attn)がencoder(self-attn)より前にあり、
クエリが位置未分化の生埋め込みであること。** markerチャンク(9,9,9,9)内の4位置は
クエリが完全に同一 → decompressorから全員が同じ情報しか受け取れない → チャンクあたり
実質1本(d_model)の情報で4桁を賄うことになり、encoder後の位置分化では取り分けきれない。
容量・ゲート・位置バイアス・層数・kv窓・クエリ縮退の全介入が無効だったのは、
どれもこの「クエリの位置盲目性」に触れていなかったから。

修正案(次の一手): **処理順をencoder(チャンク内causal self-attn) → decompressor(cross-attn)
に入れ替える**。標準Transformerデコーダブロックの順序(self-attn → cross-attn → FFN)と同じ。
encoderのALiBiで位置分化したクエリが窓を検索できるようになり、「c3の位置0はm1、位置1はm2…」
という位置別の取り分けが内積で表現可能になる。

### 順序入れ替え(self-attn→cross-attn)の検証結果と壁の完全な特徴付け (2026-08-16)
処理順をencoder(チャンク内causal self-attn)→decompressor(cross-attn)に入れ替え
(標準Transformerデコーダブロック順)。comp_queryの導出もencoder出力のチャンク末尾
(=チャンク全体のcausal要約)に変更。step/forward等価性維持、全テストパス。

結果: **T=1は0.5295で壁は不変** — クエリ位置盲目性仮説も棄却。

しかし壁の正体を数値的に完全特定:
* **bag-only最適値(4桁の多重集合は完全に分かるが順序が全く分からない場合の理論上限)
  = 0.4121 (厳密計算)。観測された中間桁accuracy = 0.4110 でほぼ完全一致**
* 予測がmemory bag内である率 = 100.0% → **多重集合の情報は完璧に伝わっている**
* 全体: (2×1.0 + 8×0.412)/10 = 0.530 = 全構成が収束した値そのもの
* 全介入(容量/ゲート/ALiBi/層数/kv窓/縮退解消/処理順)が無効だった理由:
  どれも「順序情報が値空間に存在しない」ことを解決していないから

機構的説明: **ALiBiはattentionの重みを歪めるだけで、value空間に位置タグを刻まない**。
圧縮 z = Σ_j softmax_j · W_v e_j は「どの桁が入っているか」(bag)は完全に保持するが、
「どの位置にあったか」はsoftmax重みの微差にしか残らず、デコード側で復元できない。
bagが100%伝わり順序が0%という観測はこの機構と正確に整合する。

修正案(本命): **チャンク内位置埋め込み(chunk_size個, d_model)をチャンク化直後の
トークンに加算する**。値空間に位置タグが入り、圧縮ベクトル内で「位置jの桁」が
線形分離可能になる。チャンク内C個のみ・全レベル共有・長さ非依存なので
無限生成の設計目標と両立(レベル別pos_embとは異なる)。copy実験開始時点の
アーキテクチャにはこの種の加算型位置埋め込みが存在しなかった。

### 【ブレークスルー】チャンク内位置埋め込みで壁を突破 (2026-08-16)
`chunk_pos_emb (chunk_size, d_model)` (学習可能、std=0.02初期化)をチャンク化直後の
トークンに加算(全レベル共有・長さ非依存・無限生成と両立):

* **T=1: 1500ステップで token/string ともに100%** (壁0.53を完全突破)
* T~U[1,16]・全位置loss(以前6000stepチャンス張り付きだった設定): 同6000stepで
  tok 0.97 / str 0.79、訓練域内T=4/8でstr 0.83-0.84、T=16で0.52(上昇中)
* bag-order理論の完全な検証: ALiBi(重み側の位置)だけでは圧縮の値空間に順序が
  刻まれない。値空間への位置タグ(chunk_pos_emb)が欠けていた唯一のピースだった
* 訓練域外(T=32/64)への外挿はこのスケール(d=128, 6k step)ではまだ0 —
  次のマイルストーンは本実験(d=512, 50k step, T~U[1,2028])での長さ汎化測定

これまでの改善の総括(全てコミット済みで本体に残る):
1. gate開放初期化 — 信号伝播改善(微益)
2. ALiBi(encoder/compressor/decompressor) — 重み側の位置情報・長さ非依存
3. retrieve_size kv窓 — 過去kチャンクの個別参照(検索構造)
4. クエリ別バイアス — compress_size>1の縮退解消
5. self-attn→cross-attn順序 — クエリの位置分化(標準デコーダ順)
6. chunk_pos_emb — 値空間の位置タグ(決定打)

### 層数の検証結果 (2026-08-16)
「2層では記憶/読み出しの分業に障害があるのでは」の仮説を確認するため、T=1同一条件
(d=128, answer loss, lr 1e-3, 3000step)で層数だけ変更:
* 2層: 0.528 / 3層: 0.530 / 4層: 0.530 — **完全に同じ壁、仮説は棄却**
* 全構成(ベースライン/ゲート開放/ALiBi/3層/4層)が0.52-0.53に収束する事実は、
  層数・容量・ゲート・位置バイアスのいずれでもない**情報経路そのものの構造的
  ボトルネック**を強く示唆。デコンプレッサのkv=圧縮1点の粒度問題(チャンク境界と
  桁窓の非整合)が残る本命仮説
